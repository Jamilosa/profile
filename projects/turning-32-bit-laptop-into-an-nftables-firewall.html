Turning 32-bit laptop into an nftables Firewall

Title: Turning 32-bit laptop into an nftables Firewall

Date: Jun 14, 2026
Tags: Network Security Firewall Log Management Linux nftables rsyslog

Project Summary

This project repurposed a retired 32-bit laptop into a Linux-based firewall for a small cybersecurity lab. Using AntiX Linux, nftables, dnsmasq, rsyslog, and logrotate, the firewall provides network address translation (NAT), stateful packet filtering, DNS sinkholing, and centralized logging. The implementation was validated through connectivity, domain-blocking, and traffic-filtering tests while addressing challenges associated with aging hardware and limited resources.

I. Introduction

1.1 Context & Purpose

Firewall is one of the most common and crucial defenses for network security. It controls incoming and outgoing traffic based on predefined rules. Due to limited resources, I am using an old laptop running on 32-bit AntiX Linux. The firewall will use the nftables, the default backend firewall of Linux.

1.2 What This Covers
  • Configure network configuration for the AntiX Linux.
  • Configure AntiX Linux as a nftables firewall and DNS sinkhole.
  • Configure Log rotation.
  • Configure Lab Router for the lab.
  • Apply, test, and verify basic firewall rules.

Rationale

By setting the interface names to something more intuitive like lan0 and wan0, it will be easier for the future to manage, test, and troubleshooting in the future.

Renaming wan0 and lan0 interface

3.1.2 Configure AntiX as nftables firewall and DNS sinkhole
  1. I enabled IP forwarding and Network Address Translation (NAT) on the firewall.
Rationale

The default policy on all chains for table inet filter was set to drop following a Zero Trust approach where all connections are denied unless explicitly allowed.

Initial nftables firewall config

The logging prefix on my config will follow the pattern NFT-[CHAIN]-[ACTION]-[KEYWORD] to make logs easier to analyze and because the action is not included on nftables logs by default.

3.2 Challenges & Fixes
Challenges Probable Cause Fixes
I was not able to find and install an operating system that worked for the laptop. - Support on 32-bit OS are being dropped by maintainers.
- USB ports might also be faulty.		 - I tried many lightweight 32-bit operating systems as recommended by Reddit users.
- I installed the operating systems on a different machine then swap it back to the old laptop to see if it would boot.
Overheating, low memory, low capacity storage, clock/time issues. - Dried thermal paste and dust blocking the airflow.
- Built-in memory was quite low.
- Storage type was HDD.		 - Replaced thermal paste and cleaned the fans.
- Used external fan for extra air flow.
- Added extra 2GB or RAM
- Swapped with higher capacity SATA SSD.
Time does not match with the real time and devices on the network. - Oscillator drift from aging hardware. - Swapped a new CMOS battery and used chrony to resync to the correct time.
Unfamiliar with nftables syntax. - I used iptables before and decided to switch to nftables - Viewed documentations/blogs/videos and used genAI tools about nftables.
Designing a correct cybersecurty network architecture with limited resources. - Lack of first-hand experience on real world cybersecurity environment and enterprise resources. - Utilized the available resources by designing a simplified cybersecurity lab.
USB to ethernet adapter was not recognized by the firewall. dmesg -w: device descriptor read/64, error -71, device not accepting address, unable to enumerate USB device - Daisy-chained connection (laptop -> USB-A to USB-C -> USB-C to Ethernet).
- USB ports might also be faulty.		 - Modified boot parameter by adding delay=5 as USB errors pop up immediately after turning on the computer.
- Modified boot parameter with pci=noehci to force downgrade to USB1.1.
- Ended up using the built-in wireless interface instead.

IV. Observations & Insights

  • The internet connection on the lab network (firewall's wan0 interface) is really slow. The wireless adaptor only supports 802.11a/g standards which can theoretically handle only up to 54Mbps. This is the bottleneck is in terms of connection speed for the lab.
  • dns.log and nftables.log have different log formats. This is likely true for a lot of applications and services. In order to properly parse them on the SIEM, I need to use different decoders.
  • nftables is mainly for filtering Layer 3 (Network) and Layer 4 (Transport) traffic. It can also act as a stateful firewall.
  • For blocking domains, using IP ranges could potentially cause inconvenience and holes on the network. Many modern websites are being delivered or tunneled via the massive IP blocks of companies like Cloudflare. DNS Sinkholing solves this specific problem.
  • Devices generate a lot of DNS query. While it might be useful to log for correlation and attack mapping, it will also be accompanied with a lot of noise.
  • I tried triggering a firewall drop rule and the log shows it was triggered on a different time. The longer the inaccuracy on the time, the more it would be confusing to correlate them especially across multiple hosts. This shows the importance of synchronized time across systems.

VI. Conclusion

This project successfully turned and old 32-bit laptop into a functioning firewall for my simple cybersecurity lab. It provided network address translation, network and transport layer filtering, along with stateful filtering using nftables. It also functions as dns sinkhole for blocking domains using dnsmasq. Logs are recorded on the firewall for log correlation and analysis. The logs are also rotated to prevent storage issues.

While working in this project, I realized the limitations of L3/L4 firewalls in network security. That's why I added domain sinkholing on the go to try and imitate the basic network security capabilites most real world corporate network have. I also learned the critical value of syncing time across systems as it is one of the fields used for correlation.

In the next entries, I would setup a Wazuh server that will store logs of lab hosts. Having a centralized place to view and correlate logs would make it easier to discover anomalies on the network. I will also install and attack a windows server and vulnerable hosts in the lab.
